Inventory Replenishment Agent¶

An agent that checks stock for each SKU every day, forecasts demand with EWMA, sizes safety stock from forecast error and the target service level, and decides to ORDER (respecting min_order_qty) or WAIT. A day-by-day simulation receives purchase orders after the lead time and scores the agent against a simple fixed-rule baseline.

1. Design document¶

Agent goal. For every SKU, keep customers supplied (few stockouts, high fill rate) at the lowest total cost (holding + stockout + ordering). The agent runs once per day (review period R = 1 day).

Inputs (per SKU, per day)

Input Source
Demand forecast (units/day) and forecast error (RMSE) EWMA over sales.csv, updated daily
On-hand stock, open purchase orders (qty + arrival day) simulation state, starting from inventory.csv
Lead time, service level, min order qty, costs params.csv

Output. One decision per SKU per day: ORDER q units or WAIT, plus a one-line rationale written to the daily log.

Decision rule. Look ahead over the protection period L + R (the time until a new order could next be replenished). Project stock day by day: on-hand + arriving POs − forecast × days. If the projected stock at the end of the period falls below safety stock, order up to S = forecast × (L+R) + safety stock; otherwise wait, because ordering early only adds holding cost.

Guardrails & business rules

  • Min order qty: every PO is at least min_order_qty; the log says when MOQ forced a larger order than needed.
  • Lead time: orders arrive exactly lead_time_days later; the projection counts only stock that can physically arrive in the window, and warns when a stockout will happen before a new PO can land.
  • Service level → safety stock: SS = z(service_level) × σ_error × √(L+R).
  • No over-ordering: one PO never covers more than max_cover_days (30) of forecast demand, and the agent never orders while projected stock is already above safety stock.
  • Holding vs. stockout trade-off: a higher service level buys fewer stockouts with more stock on hand. Section 10 measures that curve rather than assuming it.

Metrics

  • Stockouts: units of demand not served (lost sales) and the number of SKU-days with any unmet demand.
  • Fill rate: units served ÷ units demanded.
  • Total cost: holding (on_hand × holding_cost_per_day) + stockout (lost_units × stockout_cost) + ordering (fixed cost per PO). Purchase spend (qty × unit_cost) is tracked separately as working capital.

Ethics & trust. A stockout breaks a promise to a customer, and excess stock ties up the business's cash and can become waste. The agent treats both as real costs instead of maximizing one at the expense of the other. Every decision is logged with the numbers behind it (forecast, safety stock, projection, MOQ effect), so a planner can audit, question or override it. The agent recommends; people keep the final say.

3. Data¶

generate_sample_data() writes the three CSVs only if they don't exist yet, so you can drop in your own files. The synthetic data covers 3 SKUs × 90 days:

  • SKU-A: fast mover with a weekly cycle
  • SKU-B: growing demand (15 → 35 units/day) with weekend peaks, which a static rule can't keep up with
  • SKU-C: slow, expensive item with promo spikes

Each day's sales are split into 1–3 transactions (and zero-sale days have no rows), so the loader has to aggregate them and fill the gaps.

def load_data(data_dir: Path = DATA_DIR):
    """Load the three CSVs, check their columns and that every SKU has stock + params."""
    frames = {}
    for name, cols in REQUIRED_COLUMNS.items():
        df = pd.read_csv(data_dir / name)
        missing = cols - set(df.columns)
        if missing:
            raise ValueError(f"{name} is missing columns: {sorted(missing)}")
        frames[name] = df

    sales = frames["sales.csv"]
    sales["date"] = pd.to_datetime(sales["date"])
    sales["qty_sold"] = pd.to_numeric(sales["qty_sold"], errors="coerce").fillna(0).clip(lower=0)
    inventory = frames["inventory.csv"].set_index("sku")
    params = frames["params.csv"].set_index("sku")

    skus = set(sales["sku"])
    for label, table in (("inventory.csv", inventory), ("params.csv", params)):
        if not skus <= set(table.index):
            raise ValueError(f"{label} has no row for: {sorted(skus - set(table.index))}")
    if not params["service_level"].between(0.5, 0.9999).all():
        raise ValueError("service_level must be between 0.5 and 0.9999")
    return sales, inventory, params


def aggregate_daily_demand(sales: pd.DataFrame) -> pd.DataFrame:
    """Total units per SKU per calendar day. Days with no sales become 0, not missing."""
    daily = sales.groupby(["date", "sku"])["qty_sold"].sum().unstack("sku")

4. Forecasting¶

EWMA: forecast_{t+1} = α · demand_t + (1 − α) · forecast_t. The forecast is updated every day after that day's demand is seen, and each one-step error (actual − forecast) is stored. Their rolling RMSE is the σ used for safety stock. Setting alpha = 1.0 gives the naive forecast ("tomorrow = today").

In [5]:
class EWMAForecaster:
    """One-step-ahead EWMA forecast of daily demand that also tracks its own error."""

    def __init__(self, history, alpha: float, error_window: int):
        if not 0 < alpha <= 1:
            raise ValueError("alpha must be in (0, 1]")
        self.alpha = alpha
        self.error_window = error_window
        self.errors = []
        # Seed with the first observation, then run through the warm-up history
        self.level = float(history[0])
        for actual in history[1:]:
            self.update(actual)

    def forecast(self) -> float:
        """Expected demand per day for upcoming days (flat EWMA forecast)."""
        return max(self.level, 0.0)

    def update(self, actual: float) -> None:
        """Record today's forecast error, then move the level toward today's actual."""
        self.errors.append(actual - self.level)
        self.level = self.alpha * actual + (1 - self.alpha) * self.level

    def error_std(self) -> float:
        """Rolling RMSE of one-step errors (floored at 1 unit so safety stock never collapses to 0)."""
        recent = np.array(self.errors[-self.error_window:], dtype=float)
        return max(float(np.sqrt(np.mean(recent ** 2))) if len(recent) else 1.0, 1.0)

5. Safety stock & the replenishment agent¶

SS = z · σ · √(L + R), with z = Φ⁻¹(service_level).

Each day, for each SKU, the agent:

  1. reads the forecast and σ, computes safety stock and the order-up-to level S = f·(L+R) + SS;
  2. projects inventory day by day over the protection period L + R, counting open POs on the day they arrive;
  3. ORDERs max(S − inventory position, MOQ) (capped at max_cover_days of demand) if the projected end stock is below SS, otherwise WAITs;
  4. returns its decision with a plain-English rationale.

def safety_stock(service_level: float, error_std: float, lead_time: int, review_period: int) -> float:
    """Units of buffer stock so demand over L+R is covered with probability = service_level."""
    z = NormalDist().inv_cdf(service_level)
    return z * error_std * math.sqrt(lead_time + review_period)


@dataclass
class Decision:
    action: str          # "ORDER" or "WAIT"
    qty: int
    rationale: str
    forecast: float = float("nan")
    safety_stock: float = float("nan")
    projected_end: float = float("nan")


class ReplenishmentAgent:
    """Daily forecast -> project -> decide loop for one SKU."""
    name = "Agent (EWMA)"

    def __init__(self, sku, sku_params, history, config: AgentConfig):
        self.sku = sku
        self.cfg = config
        self.lead_time = int(config.lead_time_override or sku_params["lead_time_days"])
        self.moq = int(sku_params["min_order_qty"])
        self.holding_cost = float(sku_params["holding_cost_per_day"])
        self.service_level = float(config.service_level_override or sku_params["service_level"])
        self.forecaster = EWMAForecaster(history, config.alpha, config.error_window)

    def observe(self, demand: float) -> None:
        self.forecaster.update(demand)          # forecast updates every day

    def project_inventory(self, today: int, on_hand: float, pipeline, daily_fc: float, horizon: int):
        """Projected end-of-day stock for each of the next `horizon` days (no new orders)."""
        projection = []
        for d in range(1, horizon + 1):
            arriving = sum(q for arrive_day, q in pipeline if arrive_day <= today + d)
            projection.append(on_hand + arriving - daily_fc * d)
        return projection

    def decide(self, today: int, on_hand: float, pipeline) -> Decision:
        f = self.forecaster.forecast()
        sigma = self.forecaster.error_std()
        L, R = self.lead_time, self.cfg.review_period
        horizon = L + R
        ss = safety_stock(self.service_level, sigma, L, R)
        order_up_to = f * horizon + ss
        on_order = sum(q for _, q in pipeline)
        position = on_hand + on_order

        projection = self.project_inventory(today, on_hand, pipeline, f, horizon)
        projected_end = projection[-1]
        state = (f"on-hand {on_hand:.0f}, on-order {on_order:.0f}, fc {f:.1f}/d, "
                 f"sigma {sigma:.1f}, SS {ss:.0f}")

        # Early warning: a stockout before a PO placed today could arrive (day L)
        early_short = next((d + 1 for d, p in enumerate(projection[:L - 1]) if p < 0), None)
        warning = f" | WARNING: projected stockout in {early_short}d, before a new PO can land ({L}d)" if early_short else ""

        if projected_end >= ss:
            extra_holding = self.moq * self.holding_cost
            return Decision("WAIT", 0,
                            f"WAIT  | {state} | projected stock in {horizon}d = {projected_end:.0f} >= SS {ss:.0f}; "
                            f"ordering now would only add ~${extra_holding:.2f}/day holding{warning}",
                            f, ss, projected_end)

        need = math.ceil(order_up_to - position)
        qty = max(need, self.moq)                                   # guardrail: respect MOQ
        cap = max(self.moq, math.ceil(f * self.cfg.max_cover_days))  # guardrail: no over-ordering
        notes = []
        if qty > need:
            notes.append(f"MOQ raised qty from {need} to {self.moq}")
        if qty > cap:
            qty = cap
            notes.append(f"capped at {self.cfg.max_cover_days}d of demand ({cap})")
        note = ("; " + "; ".join(notes)) if notes else ""
        return Decision("ORDER", qty,
                        f"ORDER | {state} | projected stock in {horizon}d = {projected_end:.0f} < SS {ss:.0f} "
                        f"-> order {qty} to reach S={order_up_to:.0f}, arrives in {L}d{note}{warning}",
                        f, ss, projected_end)

6. Baseline policy (fixed reorder rule, no forecast)¶

A rule many small shops use: compute average demand once from the warm-up period, then reorder a fixed quantity (max(MOQ, 14 days of average demand)) whenever inventory position drops to average × lead time. No safety stock, no daily updates.

class FixedReorderBaseline:
    """Static (s, Q) rule: reorder Q when inventory position <= s. Never updates."""
    name = "Baseline (fixed s,Q)"

    def __init__(self, sku, sku_params, history, config: AgentConfig):
        avg = float(np.mean(history))
        self.lead_time = int(config.lead_time_override or sku_params["lead_time_days"])
        self.moq = int(sku_params["min_order_qty"])
        self.reorder_point = avg * self.lead_time
        self.order_qty = max(self.moq, math.ceil(avg * 14))

    def observe(self, demand: float) -> None:
        pass                                     # static rule: ignores new information

    def decide(self, today: int, on_hand: float, pipeline) -> Decision:
        position = on_hand + sum(q for _, q in pipeline)
        if position <= self.reorder_point:
            return Decision("ORDER", self.order_qty,
                            f"ORDER | position {position:.0f} <= s {self.reorder_point:.0f} -> fixed Q {self.order_qty}")
        return Decision("WAIT", 0, f"WAIT  | position {position:.0f} > s {self.reorder_point:.0f}")

7. Simulation engine & KPIs¶

Daily sequence for each SKU:

  1. Receive POs due today (placed lead_time days ago).
  2. Serve demand from on-hand stock. Unmet demand is a lost sale (stockout).
  3. Cost the day: holding on end-of-day stock, stockout cost on lost units.
  4. Policy observes today's demand (forecast update), then decides ORDER/WAIT. A new PO joins the pipeline with arrival day = today + L.

The first warmup_days of history only seed the forecast. Simulation starts after them with the opening stock from inventory.csv.

def simulate(policy_cls, daily_demand, inventory, params, config: AgentConfig = CONFIG):
    """Run one policy over all SKUs. Returns a day-by-day log DataFrame."""
    rows = []
    for sku in daily_demand.columns:
        p = params.loc[sku]
        series = daily_demand[sku].values
        history, horizon_demand = series[:config.warmup_days], series[config.warmup_days:]
        dates = daily_demand.index[config.warmup_days:]

        policy = policy_cls(sku, p, history, config)
        on_hand = float(inventory.loc[sku, "opening_stock"])
        pipeline = []                                   # list of (arrival_day, qty)

        for day, (date, demand) in enumerate(zip(dates, horizon_demand)):
            # 1. receive POs that arrive today
            received = sum(q for arrive, q in pipeline if arrive == day)
            pipeline = [(a, q) for a, q in pipeline if a != day]
            on_hand += received

            # 2. serve demand, unmet demand is lost
            served = min(on_hand, demand)
            lost = demand - served
            on_hand -= served

            # 3. daily costs
            holding = on_hand * p["holding_cost_per_day"]
            stockout = lost * p["stockout_cost"]

            # 4. learn from today, then decide
            policy.observe(demand)
            decision = policy.decide(day, on_hand, pipeline)
            order_cost = 0.0
            if decision.action == "ORDER" and decision.qty > 0:
                pipeline.append((day + policy.lead_time, decision.qty))
                order_cost = config.fixed_order_cost

            rows.append({
                "policy": policy.name, "sku": sku, "day": day + 1, "date": date.date(),
                "demand": demand, "received": received, "served": served, "lost": lost,
                "on_hand": on_hand, "on_order": sum(q for _, q in pipeline),
                "action": decision.action, "order_qty": decision.qty,
                "forecast": decision.forecast, "safety_stock": decision.safety_stock,
                "holding_cost": holding, "stockout_cost": stockout, "order_cost": order_cost,
                "purchase_spend": decision.qty * p["unit_cost"], "rationale": decision.rationale,
            })
    return pd.DataFrame(rows)


def kpis(log: pd.DataFrame, by=("policy",)) -> pd.DataFrame:
    """Stockouts, fill rate and cost KPIs from a simulation log."""
    g = log.groupby(list(by))
    out = pd.DataFrame({
        "demand_units": g["demand"].sum(),
        "lost_units": g["lost"].sum(),
        "stockout_days": g["lost"].apply(lambda s: int((s > 0).sum())),
        "fill_rate": g["served"].sum() / g["demand"].sum(),
        "avg_on_hand": g["on_hand"].mean(),
        "purchase_orders": g["action"].apply(lambda s: int((s == "ORDER").sum())),
        "holding_cost": g["holding_cost"].sum(),
        "stockout_cost": g["stockout_cost"].sum(),
        "order_cost": g["order_cost"].sum(),
    })
    out["holding+stockout"] = out["holding_cost"] + out["stockout_cost"]
    out["total_cost"] = out["holding+stockout"] + out["order_cost"]
    out["purchase_spend"] = g["purchase_spend"].sum()
    return out

def format_agent_log(log: pd.DataFrame) -> str:
    """Readable daily log: what happened today, then the decision and why."""
    lines = []
    for sku, part in log.groupby("sku"):
        lines.append(f"\n===== {sku} =====")
        for r in part.itertuples():
            recv = f"recv {r.received:>4.0f}" if r.received else " " * 9
            short = f"  SHORT {r.lost:.0f}" if r.lost else ""
            lines.append(f"{r.date}  day {r.day:>2}  demand {r.demand:>3}  {recv}  end {r.on_hand:>4.0f}{short}")
            lines.append(f"      {r.rationale}")
    return "\n".join(lines)

Reflection on trade-offs¶

What the numbers show (76 simulated days, 3 SKUs):

  • Agent vs. baseline. The fixed (s, Q) rule reaches only 91.0% fill rate, loses 501 units over 34 stockout SKU-days, and costs $12,076** in total. The EWMA agent reaches **99.6%**, loses **25 units** (5 stockout days), and costs **$4,309 (−64%). Holding cost is about the same for both (~$2.3k). The baseline doesn't buy service with extra stock, it just puts stock in the wrong place: it overstocks SKU-A (259 units on hand on average vs. 143) and starves SKU-B, whose demand grows from 15 to 35/day while the rule stays tuned to the first two weeks (430 lost units).
  • What the agent pays for it. More frequent, smaller orders: 58 POs vs. 19 ($1,450 vs. $475 in fixed order cost). The extra order cost is small next to the $8.7k in avoided stockout cost, but with a higher cost per PO the agent should start batching orders (an EOQ-style quantity), not just order up to S.
  • Forecast quality is a cost driver. The naive forecast (α = 1) reaches the same fill rate, but its noisy errors inflate σ and therefore safety stock: holding cost nearly doubles ($4,421) and SKU-C carries 113 units on average instead of 35. In the alpha sweep, α ≈ 0.1–0.3 works best and α ≥ 0.5 adds holding cost quickly.
  • Service level has diminishing returns. Moving the target from 0.80 to 0.99 raises average stock from 82 to 105 units but fill rate only from 99.4% to 99.6%. Total cost is lowest at 0.90 ($4,188). Above 0.95 we pay ~$370 more in holding for zero extra units served. Two things cap the benefit here: (1) minimum order quantities already act as a buffer (51 of 58 POs were rounded up to MOQ), and (2) the remaining ~23 lost units happen in the first days of the run, when opening stock runs out before any PO can arrive. Only higher opening stock or a shorter lead time fixes those, not a higher safety factor.

Takeaway. Inventory and service trade off against each other, but not linearly. The biggest gain comes from reacting to demand (forecasting + daily review). After that, each extra point of service costs more stock than the last. The right service level depends on the SKU: high for cheap, high-margin, fast movers where a stockout loses a customer, lower for expensive slow movers like SKU-C, where holding cost dominates.

Caveat: qty_sold is treated as true demand. In real data, sales on stockout days understate demand (censored data), so a production version should flag those days and impute demand for them.

11. Scaling note¶

Cloud deployment. Package the agent as a container image and run it as a scheduled job once a day after the sales close (Cloud Run Jobs / AWS ECS scheduled task / Airflow DAG). Inputs come from the warehouse (sales, stock, open POs, supplier params) instead of CSVs. Output is a table of recommended POs plus the rationale log, sent to the ERP as draft POs a buyer approves. SKUs are independent, so the job shards by SKU or category and runs in parallel.

Monitoring. Track daily per SKU and category: fill rate, stockout days, forecast error (MAE, bias) and inventory value. Alert when fill rate drops below target for 3+ days, when forecast bias stays one-sided (the model has drifted), or when a SKU's order volume jumps far above its history. Every rationale line is stored for audits.

Reliability. Retry data loads with backoff and make runs idempotent (re-running a day doesn't duplicate POs, because they're keyed by SKU + date). Handle missing data explicitly: no sales rows means 0 demand only if the store was open; a missing feed should pause ordering for that SKU, not order on zeros. Validate inputs (schema, negative stock, missing params) and fall back to the last good forecast on failure.

Cost controls. Enforce guardrails outside the model: a per-SKU inventory cap (max days of cover), a daily and weekly working-capital budget (sum of qty × unit_cost), and human approval for POs above a $ threshold. Report holding cost and inventory turns next to fill rate, so the service target is always weighed against the cash it consumes.
